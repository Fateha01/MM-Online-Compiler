# MM_compiler — Mini Language Compiler (Compiler Construction Lab Project)

A compiler front-end (lexer → parser/AST → semantic analysis → three-address
code generation) for a small imperative language with `int`/`float`/`bool`
types, arithmetic/relational/logical expressions, `if`/`if-else`, `while`,
`print`, and properly scoped nested blocks — built with **Flex** and
**Bison**, per the Compiler Construction Lab project manual.

> **Note on naming:** the project folder/repo is `MM_compiler`. The
> compiled binary and internal build commands still use the name
> `mc-compiler` (e.g. `./mc-compiler file.mc`, `make` targets) — only the
> outer project name changed, not the binary itself, to avoid touching
> the dozens of already-tested references to it across the Makefile,
> `.vscode/` tasks, `demo/backend/server.py`, and this README. If you'd rather
> the binary itself be renamed too, that's a bigger, riskier change —
> ask and it can be done carefully with full re-testing.

## Requirements

`flex`, `bison`, `gcc`, `make` (and `gdb` if you want to use the VS Code
debug config). Two ways to get these, pick whichever matches your setup:

**Option A — Linux, or Windows with WSL:**
```
sudo apt update
sudo apt install flex bison gcc make gdb
```

**Option B — Windows, no WSL (via MSYS2):**
1. Install [MSYS2](https://www.msys2.org/) (default path `C:\msys64`)
2. Open the **"MSYS2"** shortcut from the Start menu once, run:
   ```
   pacman -Syu
   ```
   (it may close itself and ask you to reopen "MSYS2" and run `pacman -Syu`
   again — that's normal, do it until it says there's nothing left to update)
3. Open the **"MSYS2 UCRT64"** shortcut from the Start menu (a different
   shortcut from step 2) and run:
   ```
   pacman -S --needed base-devel mingw-w64-ucrt-x86_64-toolchain flex bison
   ```
4. Verify: `gcc --version`, `flex --version`, `bison --version`, `make --version`, `gdb --version`

This project's `.vscode/settings.json` and `.vscode/tasks.json` are already
configured to use the MSYS2 UCRT64 environment automatically when you open
this folder in VS Code on Windows — see "Using VS Code" below. You do not
need to edit your system PATH.

## Build

```
make
```

This runs Bison on `src/parser/parser.y` (generating `parser.tab.c` /
`parser.tab.h`), runs Flex on `src/lexer/lexer.l` (generating `lex.yy.c`),
compiles every module, and links them into an executable in the project
root — `mc-compiler` on Linux/WSL, `mc-compiler.exe` on Windows (the
Makefile detects which and names it correctly either way; the run command
below, `./mc-compiler ...`, works unchanged on both, since MSYS2's bash
resolves it to `mc-compiler.exe` automatically).

## Run

```
./mc-compiler tests/valid_program.mc
```

This prints, in order: parse status, semantic analysis status, the AST, and
finally the generated three-address code. If a lexical, syntax, or semantic
error is found, the compiler reports it (with a line number) and stops
before the next phase — it does not attempt to generate TAC for a program
that didn't pass semantic analysis.

## Run every test program at once

```
make test
```

Runs `mc-compiler` against every `.mc` file in `tests/`, one after another.
Compare the output against the matching `tests/*.expected.txt` file.

## Clean up generated files

```
make clean
```

Removes the build directory, the executable, and the Flex/Bison-generated
`.c`/`.h` files (these are regenerated by `make` and are intentionally not
committed to git — see `.gitignore`).

## Using VS Code instead of the terminal

The project ships with a `.vscode/` folder, so opening the `mc-compiler`
folder in VS Code (`File → Open Folder…`) gives you working build/run/debug
integration out of the box:

- **`Ctrl+Shift+B`** — runs the default build task (equivalent to `make`)
- **Terminal → Run Task… → "Run all tests (make test)"** — builds, then runs
  every program in `tests/`
- **Terminal → Run Task… → "Run on current file"** — compiles whichever
  `.mc` file you currently have open in the editor
- **Run and Debug panel (`Ctrl+Shift+D`) → "Debug mc-compiler (gdb)"** —
  builds, then launches under gdb; it will prompt you for which `.mc` file
  to pass as an argument (defaults to `tests/valid_program.mc`), so you can
  set breakpoints in `semantic.c`/`codegen.c`/etc. and step through a real
  compilation.
- On first open, VS Code will suggest installing the **C/C++ extension**
  (`ms-vscode.cpptools`) — accept that for IntelliSense to work.

**On Linux/WSL:** nothing else to configure — open the folder from inside
your Ubuntu/WSL terminal with `code .`, not from a plain Windows Explorer
window, so `make`/`flex`/`bison`/`gcc` are actually on PATH.

**On Windows without WSL (MSYS2):** as long as MSYS2 is installed at the
default `C:\msys64` (see Option B above), just open this folder directly in
VS Code — `.vscode/settings.json` and `.vscode/tasks.json` already point
the integrated terminal and every task at the MSYS2 UCRT64 environment, so
`Ctrl+` ` `` and `Ctrl+Shift+B` work with no further setup. If you installed
MSYS2 somewhere other than `C:\msys64`, update that one path in both of
those files (search for `msys64`) to match.

> **Honesty note on the Windows/MSYS2 path:** this configuration follows
> MSYS2's own documented setup (pacman, the UCRT64 environment, the
> standard VS Code terminal-profile pattern for it) and the Linux/WSL build
> of this exact codebase was fully build-tested, run against every test
> case, and checked with `valgrind`/`gdb`. The MSYS2/Windows path itself
> could not be executed end-to-end in the environment this project was
> prepared in (no Windows machine available there), so if any step doesn't
> match what actually happens on your machine, that's useful information —
> note the exact error and it can be fixed precisely rather than guessed at.

**Note on IntelliSense before the first build:** `lexer.l` includes
`parser.tab.h`, which is generated by Bison and doesn't exist until you
build once. It's normal to see a red squiggly under that include the very
first time you open the project — run the build task once and it clears up.

## Combined Demo (optional — Section 14 bonus feature: GUI)

`demo/` is one local web page with a language dropdown: **Mini Language
(mc-compiler)** — the actual graded compiler below — plus C, C++,
Python, Java, and JavaScript via their real toolchains, for general
demo/exploration purposes.

**Be precise about the boundary, since one page covers two different
things:** picking "Mini Language" in the dropdown runs the real,
compiled `mc-compiler`/`mc-compiler.exe` binary from `src/` — the exact
same lexer/parser/semantic-analyzer/codegen graded per Section 4 of the
manual, showing the same phase-by-phase pipeline (Lexer → Parser →
Semantic + Symbol Table → AST → TAC) as the CLI. Picking any other
language in the dropdown runs a real, separate toolchain (gcc, g++,
python3, javac+java, node) and **has nothing to do with the
coursework** — the manual requires one fixed mini-language (Section 3),
so that code path never touches `src/`, isn't built by `make`, and
shouldn't be presented as part of this project's deliverable. It's in
the same page purely for convenience of one frontend instead of two.
Full detail on exactly where that line is: `demo/README.md`.

**To run it:**
```
cd demo/backend
python3 server.py
```
(or double-click `demo/run_demo.bat` on Windows, or run `demo/run_demo.sh` —
both of those build the compiler first via `make`, then start the server;
running `server.py` directly skips that build step, so make sure you've
already run `make` in the project root at least once)

Starts a small local server (Python standard library only — no pip
installs) and opens your browser to it automatically. In VS Code:
**Terminal → Run Task… → "Start Demo"**. Everything runs on `localhost`
— no internet connection needed once Python itself is installed, which
matters if the demo room has no wifi.

**Requirements:** Python 3 for the demo itself (already commonly
present on Windows; on MSYS2, `pacman -S mingw-w64-ucrt-x86_64-python`
if missing). The Mini Language option only needs `make` run once first;
the other languages only appear in the dropdown if their toolchain is
actually installed — see `demo/README.md` for install steps per
language, all optional.

## Feature Summary

- **Lexer**: keywords, identifiers, int/float/bool literals, all required
  operators/delimiters, comments discarded, invalid characters reported as
  lexical errors with line numbers.
- **Parser**: full CFG for the language (see `docs/report.md` Section 3.3),
  builds an AST, basic panic-mode error recovery on syntax errors.
- **AST**: printable, indented tree for every construct in the language.
- **Symbol table**: nested/block scoping, tracks name/type/scope-depth/
  declared-line for every symbol; prints the full table (in declaration
  order) once a program passes semantic analysis with no errors.
- **Semantic analysis**: undeclared variable, redeclaration, scope
  violation, type mismatch, invalid assignment, invalid expressions — all
  six required categories, each with a distinct, line-numbered message.
- **TAC generation**: arithmetic (with correct precedence), relational/
  logical expressions, `if`/`if-else`/`while` via labels and jumps, `print`.
